# AutoCheckin

Telegram 多账号签到与消息自动化工具，提供本地 Web 管理界面。Node.js 负责配置管理、日志与任务调度，Python / Telethon 负责 Telegram 操作。

> **网页使用用户名和密码登录，不开放注册。管理员默认用户名为 `admin`，密码由 `ADMIN_PASSWORD` 配置，可在「用户管理」创建普通用户。默认监听所有 IPv4 网卡，Docker 发布 `8765` 端口，不限制访问域名或客户端 IP；公网访问必须使用 HTTPS 反向代理。** `config.json`、Telegram Session 和备份均包含敏感数据，请妥善保存。

## 功能

- **多账号管理**：全局 Telegram API 凭据统一配置，账号可逐字段覆盖；Session、签到 Bot 与对话分组仍独立保存。
- **自定义排序**：账号卡片、Bot 列表、签到定时任务、定时消息、转发、清理群员与抢红包规则支持拖动排序，自动保存；不同网页用户独立，刷新和重启后保留。
- **功能中心**：管理员和普通用户均可进入。「Bot 自动签到」集中管理各账号的 Bot、账号定时、独立定时与手动执行；「监听转发并置顶」支持多个来源、多个关键词与可选置顶；「清理0发言群员」支持指定账号检测群历史、发送 Excel 名单、群内确认移出并解除限制；「抢红包」监听群内 `/red` 指令，按钮出现自动领取，支持自定义识别词。配置按用户隔离并持久化。
- **网页用户权限**：管理员创建用户；初始密码 `a123456`，首次登录强制改密。不同用户的 Telegram 账号、Session、API 凭据、Bot、任务、AI 配置、调度状态与日志完全独立且持久化。
- **系统全局服务**：管理员可设置系统 Telegram API 与 AI 提供商，用户未设置个人服务时自动继承管理员默认配置。管理员可在网页修改自己的用户名。
- **后台审计**：管理员按网页用户、Telegram 账号查看签到日志及 Bot 配置，包括签到方式、命令、备注、独立定时和对话分组识别记录。
- **TG 通知**：每位用户配置通知 Bot 和接收会话；账号定时签到、Bot 独立定时结束后推送结果，支持测试通知、发送记录与有限重试。通知按 Bot 统计成功、超时、失败及跳过；支持备注显示，未完成项目优先列出。
- **运行健康监控**：账号连接、代理可用性及签到/监听任务心跳；连续异常达到观察阈值后发送 TG 告警，恢复后通知，重复告警支持冷却间隔。用户查看自己的状态，管理员可查看系统全部用户。自动化进程支持有限次数恢复。
- **Bot 签到**：支持按钮交互和自定义命令，每个 Bot 完成后随机等待 5–15 秒再处理下一个。AI / OCR 辅助处理验证码；没有 AI 配置也能执行普通签到。
- **签到计划**：按账号配置每日或一次性任务；Bot 管理中可指定单个 Bot 的独立每日时间，不跟随整账号签到。同一网页用户的不同账号支持并行签到与批量并行，同一账号的计划与手动签到互斥，不同用户独立调度。
- **签到与监听并行**：同一 TG 账号签到时复用自动化进程已有连接，抢红包、监听转发与定时消息继续运行；不再因签到主动暂停监听。单独停止签到不关闭监听，同一账号仍只执行一项签到任务。
- **规则独立保存与日志**：已保存规则的启用开关点击后立即保存状态，不提交其他内容草稿，失败时核对已保存状态并恢复开关显示。修改配置后单独点击「保存规则」，该按钮随配置一起折叠，未修改时不可点击；新规则需先完成首次保存。「规则日志」收起后仍可使用，日志弹窗按规则标识筛选当前用户的所有保留记录，可继续按账号、日期与状态筛选。单独保存或删除一条规则不会提交其他规则的草稿；签到计划日志仅包含该计划新产生的定时记录，旧版日志和手动签到仍在「运行日志」查看。
- **折叠规则配置**：抢红包、监听转发并置顶、清理 0 发言群员、签到定时任务和定时消息统一使用可折叠卡片。已保存规则默认收起，新建规则自动展开，保存成功后收起；可单独或全部展开/收起。收起后保留账号、关键配置和运行状态，切换菜单与自动刷新保留当前页面的展开状态和未保存内容。
- **分组轮询**：在 Bot 管理中选择 Telegram 对话分组，只签到分组里的 Bot；首次识别按钮、`/sign`、`/checkin` 并记录方式。已确认无签到方式的 Bot 后续跳过；无响应或网络失败保留为待确认，可手动重新识别。
- **PostgreSQL**：Compose 一并部署数据库，持久化配置、签到日志、调度状态、账号资料和 Bot 识别记录；首次启动自动导入旧文件。
- **用户全局设置与自动继承**：每个用户（包括管理员）可在「全局设置」管理自己的 Telegram API 和命名代理，在独立的「AI 管理」中维护自己的模型与 AI 提供商。每项服务独立继承：配置了使用自己的，未配置自动使用管理员设置；支持恢复管理员配置，用户之间数据隔离并持久化。管理员和普通用户已有的个人 API / AI 配置自动迁移。
- **管理员全局设置**：独立菜单管理共享 Telegram API、命名 AI 提供商和命名代理列表，支持编辑、删除与延迟测试。旧代理和 AI 配置自动兼容。
- **多出口代理**：支持 HTTP、HTTPS、SOCKS5，可选用户名密码；每个 Telegram 账号可选择独立出口或跟随系统默认。覆盖登录、签到、AI、通知与功能插件，所选代理失败不回退直连，配置持久化保存。
- **定时消息**：按账号向指定会话发送纯文本消息。
- **监听转发**：监听群组或频道的新消息，转发至目标会话；输入 ID、用户名或公开 t.me 链接后，使用当前账号自动查询并在输入框右侧显示名称。不会重放历史消息或重新转发编辑消息。
- **账号资料**：显示 Telegram 头像、用户 ID 和当前 Session 的 DC，支持同步资料。
- **管理界面**：奶油色背景、粗描边与实色阴影，统一下拉框、日期时间控件和弹窗；适配手机，弹窗支持平滑开合。支持浏览器前进、后退和页面内链接导航，切换页面保留账号与规则草稿；下拉框支持键盘选择和 Tab 继续填写，并跟随原表单同步禁用状态。工作区右上角的「竖向菜单」开关可切换顶部横向菜单与左侧竖向菜单，选择保存在当前浏览器；手机竖向菜单可通过「菜单」按钮展开、关闭，不挤压内容。
- **配置与日志**：网页编辑配置、查看运行状态与最近日志；密钥不回显，留空保存时保留已有密钥。

日常状态刷新只读取运行状态，账号配置在首次加载或明确刷新时获取；页面切到后台后暂停状态轮询，回到前台立即刷新。群组/频道名称只在打开对应的定时消息或功能插件配置时查询。OCR 模型在首次处理图片验证码时加载，同一次签到进程内复用，普通按钮或命令签到无需预先加载模型。

## 网页用户与权限

1. 管理员使用用户名 `admin` 和环境变量 `ADMIN_PASSWORD` 登录；`ADMIN_USERNAME` 设置初始用户名。之后可在「用户管理 → 管理员账号」修改用户名并持久化，重启后使用保存的新用户名；管理员密码仍由环境变量管理。
2. 打开导航「用户管理」，填写用户名添加用户。用户名为 3–32 位字母、数字、下划线、点或短横线，忽略大小写检查重复，不接受公开注册。
3. 新用户用初始密码 **`a123456`** 登录后，只能访问改密页面。必须验证原密码并设置至少 8 位的新密码，才能进入工作台；不能继续使用初始密码或原密码。
4. 普通用户自行添加 Telegram 账号、配置 Bot、签到计划、定时消息和监听转发，只能读取和操作自己的数据。个人 Telegram 凭据、AI 配置与「全部账号日志」仅限当前网页用户。管理员用户管理页列出用户名和密码状态，不回显密码。
5. 已登录的普通用户可通过右上角「修改密码」再次改密，其他浏览器的会话会失效。服务重启后需重新登录；用户及任务数据不会消失。

管理员可在用户列表中「修改」用户名、「重置密码」或「删除」用户。修改用户名沿用原用户 ID 和全部配置，并使原登录会话失效；重置密码恢复为 `a123456`，使全部会话失效并强制下次改密。删除需确认，立即撤销访问并停止该用户后台任务；持久化数据保留供备份，不会继续调度，再次创建同名用户会获得新的空工作空间。管理员账号不在普通用户操作列表中。

### 自定义拖动排序

使用卡片或 Bot 行上的拖动手柄调整显示顺序，支持鼠标和手机触摸。也可聚焦手柄后使用方向键移动，Home / End 移到首尾，拖动中按 Esc 取消。

排序自动保存，不需要点击「保存配置」，不会提交未保存的表单草稿，也不会重启自动化或改变任务执行顺序。保存失败时恢复上次顺序，并提供「重试保存」。账号排序后，各按钮仍对应原账号。

支持账号卡片、Bot 列表、签到定时任务、定时消息、监听转发并置顶、清理 0 发言群员和抢红包规则。抢红包仅调整规则卡片显示顺序，其监听、领取等运行逻辑不变。

排序按网页用户持久化到 PostgreSQL 的独立 `ui-order` 文档；文件模式使用数据目录中的 `.ui-order.json`，切换到 PostgreSQL 时自动导入。沿用现有 Docker Compose 数据持久化配置。

### 运行健康监控

打开导航「运行健康监控」。运行中的账号复用签到或自动化进程的连接，每 10 秒报告心跳、每 60 秒验证一次 Telegram 请求；空闲账号使用独立的只读检查，检查前占用账号的 Session，避免与签到、登录或监听并行打开同一 Session。不会向群组发送检查消息。未运行的账号显示最近检查结果，而不是把存在 Session 文件视为当前在线。

定期检查默认关闭，可点击「立即检查」，或保存启用监控。默认每 120 秒检查使用中的代理与空闲账号，支持调整为 30–3600 秒。代理检查访问 Telegram HTTPS 接口，支持现有 HTTP、HTTPS、SOCKS5 出口和账号单独选择的代理；不检测未使用的代理，也不会在代理失败时回退直连。

告警默认关闭，需先在「TG 通知」保存 Bot 和接收会话，再开启「TG 异常告警」。默认连续异常 2 次且持续 60 秒才告警，同一异常每 30 分钟最多通知一次，可调整阈值、观察时间和间隔。发送异常与恢复通知均复用已有的持久化通知队列，使用当前用户默认出口，避免账号所选代理故障导致通知也被绑定到故障出口。默认出口自身故障时，通知可能无法发送，可在 TG 通知页面查看失败记录。

监控区分需要重新登录、短暂网络重连、Telegram 限流、持续断线与任务心跳超时；群内没有新消息不会被当作掉线。签到复用监听连接并行执行，正常登录或群清理而暂停监听时不告警。每条自动化规则显示共享心跳及最近正常执行时间，签到账号显示最近执行结果。

自动化进程异常退出或监控确认连接异常时，可自动恢复，默认最多追加 3 次；达到上限后停止重试，可在页面检查原因后点击「重新连接自动化」。稳定运行两分钟后重新计数，0 表示不自动重启。不会自动重跑已结束的签到或已发送的消息；原有调度去重记录继续生效。

监控设置、异常告警状态及最近 100 条异常/恢复记录按用户持久化到 PostgreSQL，文件模式使用 `.health-state.json`，切换到 PostgreSQL 时自动导入。连接观测值在服务重启后重新检查，避免展示旧在线状态。管理员通过「查看范围 → 系统全部用户」查看整体状态，此视图不提供其他用户配置的修改入口。沿用现有 Compose，不增加服务；更新后执行 `docker compose up -d --build`。

签到结束时会先卸载消息回调、等待未完成的回调取消，再标记已读和断开连接，避免收尾时出现 `Cannot send requests while disconnected` 堆栈。`Server closed the connection` 等短暂重连警告与 Bot 超时分别处理；最终成功或失败仍以实际 Bot 结果及任务退出码为准。

### 功能中心：Bot 自动签到

打开「功能中心 → Bot 自动签到」，选择执行 TG 账号后配置：

- **Bot 管理**：添加 Bot、设置命令或按钮签到、填写备注，也可切换为 Telegram 对话分组轮询。单个 Bot 的独立定时可精确到秒。
- **定时任务管理**：为当前账号设置每日、一次性或每日区间随机签到任务。
- **手动执行与日志**：执行当前账号签到，或同时执行全部账号；在插件内查看当前账号的运行日志。

签到配置与执行统一从功能中心进入；总览的「配置签到」也进入此插件。刷新插件页会保留所选账号与配置分类。

已有 Bot、备注、分组识别记录、账号定时和 Bot 独立定时继续使用原有持久化数据，无需重新配置。账号管理保留登录、资料、出口代理、定时消息和运行日志；签到配置与执行统一在功能中心。

### 功能中心：监听转发并置顶

打开「功能中心 → 监听转发并置顶 → 配置插件」，点击「添加规则」。每条规则配置：

- **执行 TG 账号**：选择当前网页用户已有的一个 Telegram 账号，该账号需完成登录。
- **监听来源**：添加 1–20 个群组或频道，支持数字 ID、@用户名或公开 t.me 链接。
- **转发目标**：指定一个群组或频道；执行账号需有访问来源及向目标发送消息的权限。输入后使用所选账号查询会话名称。
- **关键词**：可添加最多 50 个关键词，每个最多 100 字符。按文字包含匹配，忽略大小写，命中任意一个即转发；可匹配消息正文和媒体说明，不使用正则表达式。留空则转发全部新消息，包括没有文字说明的媒体。
- **转发后置顶**：可单独开关；开启时置顶目标会话中刚转发的消息，不发送置顶通知。执行账号需有目标会话的置顶权限。

填写规则名称便于识别日志，可随时添加、修改、关闭或删除规则，在对应卡片内点击「保存规则」后自动应用。账号下的转发入口已移除，所有转发规则统一在此管理。旧单来源规则升级时自动迁入，保留执行账号、启用状态、来源、目标和原有规则 ID（冲突时生成新 ID），默认不筛选关键词、不置顶；迁移后清空旧列表，避免重复转发。来源和目标不能相同，保存时会检查所有规则之间的循环。

只处理开始监听后的新消息，不重放历史消息，也不重新转发编辑消息。不同规则独立监听；某个来源解析失败会记录错误，其他有效来源仍可监听。转发和置顶结果归入「运行日志 → 监听转发」，带有执行账号和规则标识。置顶失败时记录「消息已转发，但置顶失败」，不会因为置顶重试而再次转发原消息。签到期间监听继续运行；登录或群清理期间会暂停，结束后恢复。

插件沿用现有自动化服务及配置存储，不需要额外容器或数据库表。PostgreSQL 模式和文件模式均保存到当前用户的配置，重启后恢复规则；其他网页用户不能读取或修改这些规则。

### 功能中心：抢红包

打开「功能中心 → 抢红包」，添加规则，选择已登录的执行 TG 账号与 1–20 个监听群组。支持 ID、@用户名或公开 t.me 链接，输入后自动查询群名。可限定红包 Bot（如 `@niubi_bot`），已保存规则的启用开关点击后直接保存状态，删除已保存规则立即生效。

发现新的 `/red` 或 `/red@bot` 指令后开启临时等待窗口。优先处理 Telegram 新消息及消息编辑，匹配到领取按钮立即点击；等待期间每秒补充刷新近期消息与已跟踪的红包消息，以识别“正在准备红包”随后被编辑为领取按钮的情况。默认匹配 `好運連連`、`领取红包` 等文字，只点击 Bot 的 callback 按钮。

其他群成员或执行账号发送的、以 `/red` 开头的文字均可触发。即使指令被 Bot 快速删除或实时事件漏收，也会直接识别新 Bot 消息中的准备提示与领取按钮。没有实时消息时每 5 秒补充查询新消息；启动时先记录最新消息 ID，备用查询不重放旧红包，并遵循账号的限流等待。

首次立即领取，未确认时默认每 0.5 秒重试。收到本人按钮回调的成功或已领取提示，或 Bot 的红包领完/失效提示后，停止本轮刷新并继续监听；不会将群内其他人的领取成功当作本人成功。每个账号共享去重与限流等待，同一红包的重复事件及重叠规则只启动一个领取循环，不同账号独立领取。遵循 Telegram 返回的限流时间，实际领取速度与结果取决于 Telegram 和 Bot 的响应。

支持 `niubi_bot` 将原红包编辑为「某某的红包已经被抢光啦~」并移除按钮的领完状态，收到编辑事件或刷新到这一正文即结束本轮。只移除按钮但没有明确结果时继续等待，不直接判定领完；榜单中的其他人领取记录不会被当作本人领取成功。

「识别与重试设置」可调整等待窗口（30–600 秒，默认 120 秒）、重试间隔（0.5–5 秒），以及领取按钮、成功/已领取、领完/失效识别词。每类识别词每行一个、最多 30 个、每个最多 80 字；留空使用默认词，填写则替换该类默认词。Bot 的未知结果会继续等待，不会直接判定成功；窗口超时、按钮失效或执行错误会结束本轮。并发红包优先按 Bot 回复链关联，Bot 不带回复关系时按最近的指令关联。

保存后自动监听，重启后恢复规则，不重放旧指令。日志归入「运行日志 → 抢红包」，按当前用户与 TG 账号隔离。完成的红包去重记录保留最多 7 天、2000 条，在 PostgreSQL 中按用户持久化；文件模式使用 `.red-packet-state.json`，切换到数据库时自动导入。沿用现有账号出口代理与 Compose，不需要额外服务。手动签到、账号定时和 Bot 独立定时复用正在监听的 Telegram 连接，不关闭红包监听；不同账号的签到也不停止已有监听。单独停止签到只取消本次签到。登录、群清理、配置更新或服务关闭仍会暂停监听；若签到取消后未及时释放回调，停止保护会终止自动化进程以避免继续发送，随后重新连接。监听进程意外退出时，本次签到按中断记录，不自动重发签到。

配置页显示已连接群组数、收到的实时消息数、发现的 `/red` 与红包按钮数、备用检查次数和最近接收时间。红包日志还记录群组连接、首次收到消息、Bot 用户名/按钮词不匹配、启动失败和任务暂停，便于区分未连接、没有消息和规则未命中；不会记录群内每条普通消息的正文。更新 Docker 部署需执行 `docker compose up -d --build`，以更新 Python 监听器及服务端代码。

### 功能中心：清理0发言群员

打开「功能中心 → 清理0发言群员 → 配置插件」，添加规则并选择一个已经登录的 TG 账号、一个目标群组和可选规则名称。账号需要目标群的管理员身份及移除成员权限。支持普通群组和超级群组，不支持广播频道。规则保存后不会自动执行，点击「启动检测」会先保存本条规则，再启动本次检测。

执行流程：

1. 执行账号向群内发送 `正在查看0发言人数`，获取群成员并遍历可访问的历史消息。普通文字、媒体及其他普通消息计作发言，入群、改名等服务消息不计。
2. 将检测到的0发言成员整理为 `.xlsx`，包括 **TG ID、用户名、账号名字**，附上清理说明及检测范围。没有用户名或名字也保留 ID；ID 和名字按文本保存，避免长 ID 精度丢失及公式执行。
3. 向群内发送 `群成员XX人，检测到0发言人数XX人` 并附带 Excel 文件。账号和管理员也可出现在名单中，但标记为不清理。成员列表不完整时只生成报告，不允许清理；无可清理成员则直接完成。
4. 发送 `是否踢出0发言成员（不影响后续进群），回答是或否？`。只接受**执行账号本人**在同一群中、提示发出后发送的独立文字 `是` 或 `否`；可以直接发送，也可以回复该提示。其他人、旧消息和转发的确认文字均无效。30 分钟没有回答自动取消。
5. 回答 `否`，群内发送 `已取消本次清理任务。`。回答 `是`，逐人重新检查发言、管理员身份和成员状态；已经发言、成为管理员、退群或重新入群的成员跳过。移出后解除个人限制，下一次可以按群原有规则申请进群。
6. 群内发送本次清理汇总，包括移出、跳过及失败人数。某个成员失败不会阻止其他成员处理。解除限制失败会单独记录；超级群的临时移出限制设为最多 120 秒自动到期，避免进程崩溃留下永久封禁。

**判断范围**：Telegram 不提供可靠的“此人自入群以来永远0发言”统计。插件只能判断执行账号可访问且尚未删除的历史消息。加入前不可见或已经删除的发言无法识别，所以页面、群报告和 Excel 都明确注明这一范围，清理前需根据名单判断。

检测和等待确认期间，该 TG 账号由插件占用，同账号签到会等待；其他账号仍可签到，也可并行启动已保存且未修改的清理规则。存在运行任务时不能保存配置，修改过的规则需等任务结束后再保存启动。该用户的消息自动化沿用原有机制暂停，所有占用释放后恢复。网页可查看状态、打开运行日志、停止任务、下载 Excel；日志新增「功能插件」分类。停止只终止后续处理，不会把已移出的成员拉回群。

配置、检测快照和日志在 PostgreSQL 模式下按用户持久化，文件模式也独立保存。Excel 保存在用户数据目录 `.cleanup-jobs/`，由现有 Docker 数据卷持久化；不需要新容器或依赖。目录已加入 Git 忽略。数据库首次启用时导入旧检测快照，Excel 文件保留在数据卷中。执行器通过父进程管道检测服务退出，失去服务连接即取消，防止残留进程继续清理。服务重启会将未完成任务标为中断，**不会自动继续清理或沿用上次的“是”**；需要重新启动检测并确认。

### 系统 Telegram API 与 AI 提供商

管理员可见两个独立菜单：「全局设置」只作用于管理员自己的账号；「管理员全局设置」管理整个项目的默认配置。管理员在「管理员全局设置 → 项目全局服务」设置 API ID / API Hash 与默认 AI 模型。AI 提供商以命名列表管理，可通过弹窗添加、编辑、删除，并为每条服务设置独立模型；独立模型留空时使用默认模型。Hash / Key 不回显，编辑留空保存保留原值。

点击提供商的「延迟测试」会通过系统默认出口查询其 `/models` 接口，验证认证并显示耗时，不发送聊天内容或产生生成请求。测试失败也可能是提供商不支持模型列表接口，不等同于一定不能完成签到验证码。用户可在「AI 管理」选择某个全局提供商，或按全局列表顺序尝试全部提供商。被用户选择的提供商需先解除选择才能删除。

每个用户在「全局设置」配置自己的 Telegram API 和出口代理，在「AI 管理」添加、编辑、删除、测试自己的 AI 提供商并设置默认模型。**Telegram API、AI、代理三项分别继承**：没有填写的项自动使用管理员全局配置，已配置的项优先使用用户自己的配置；不需要额外勾选启用。账号独立 API 凭据仍优先于用户全局 API。账号管理不再提供重复的共用 API 表单，个人 AI 提供商统一在 AI 管理维护，个人全局设置不再提供重复的 AI 表单；管理员共享的默认 AI 仍在管理员全局设置中配置。

升级时，管理员和普通用户的旧个人 API / AI 配置都会自动导入各自的持久化设置，分别由全局设置和 AI 管理编辑；已有配置不会覆盖，已主动清空并选择继承的项目不会恢复旧值。迁移标记随配置持久化，重启不会再次导入。

「恢复管理员 Telegram API」清除用户全局 ID / Hash；AI 管理中的「恢复管理员 AI」清除用户自己的 AI 服务列表；代理默认出口选择「跟随管理员默认出口」即可恢复继承。代理列表中保留的条目仍可单独分配给账号。AI 管理可选择一个提供商或依次尝试当前生效的默认列表，列表显示“我的 / 管理员”来源。账号代理选择也可使用自己的代理或管理员共享代理；已有单独选择保持有效。

用户只能编辑、删除、测试自己的条目，无法操作其他用户或管理员的配置；共享服务只提供无密钥摘要，不返回管理员 API Hash、AI Key 或代理地址、认证信息。用户自己的密码、Hash、Key 同样不回显，编辑时留空保留。

更新系统 Telegram API 会重新连接空闲账号的消息自动化；正在签到或扫码登录的账号在下次连接时生效。系统 AI 更新在下次签到任务启动时生效。已登录的 Telegram Session 若更换 API 后失效，需要重新登录。

PostgreSQL 将系统服务、管理员用户名保存为 `system-settings` / `admin-profile` 文档；普通用户全局设置使用 `tenant:<用户ID>:system-settings` 文档，管理员自己的全局设置使用独立的 `personal-settings` 文档，用户的选择保存在各自配置内。普通用户文件模式使用 `.user-workspaces/<用户ID>/.system-settings.json`，管理员个人配置使用 `.personal-settings.json`，切换到数据库时自动导入。文件模式使用数据目录的 `.system-settings.json` / `.admin-profile.json`，已加入 Git 与 Docker 忽略；切换到 PostgreSQL 时自动迁移，已有数据库记录不覆盖。

### 系统出口代理

管理员打开「管理员全局设置 → 出口代理列表」，点击「添加代理」，填写名称、**HTTP / HTTPS / SOCKS5** 协议、主机名或 IP、端口以及可选认证。最多保存 50 条，列表支持编辑、删除和延迟测试。地址框不包含协议前缀、端口或路径。HTTPS 表示使用 TLS 加密连接代理服务器，需使用有效证书；HTTP/HTTPS 代理需支持 CONNECT。SOCKS5 将目标域名交给代理解析。

「系统默认出口」用于未指定独立代理的账号及系统请求；选择“不使用默认代理”才会启用默认直连。每个账号的「账号资料 → 出口代理」可选择某条命名代理或跟随系统默认，保存后生效。该账号的登录、头像同步、名称查询、签到、消息自动化、功能插件及 AI 请求使用所选出口，定时签到结果的 TG 通知也沿用该账号出口；测试通知使用系统默认出口。不同用户或同一用户的多个账号可以同时使用不同代理，不会互相切换出口。

代理「延迟测试」测量通过该代理访问 Telegram HTTPS 接口的连接、TLS 握手及响应耗时，不登录、不发送 Telegram 消息，也不等同于 MTProto 签到任务耗时。结果仅保留在当前页面，不将瞬时测试结果用作自动切换依据。被账号选择的代理不能删除，需先更改账号出口；系统默认代理也需先更改默认出口后才能删除。

**HTTP、HTTPS、SOCKS5 是连接代理服务器的协议，不限制被代理的目标服务协议。** 例如选择 HTTP 代理后，Telegram TCP 连接和 HTTPS 的 AI 请求也会通过该代理。

项目统一通过所选代理上网，覆盖所有网页用户的 Telegram 扫码登录、账号资料与头像同步、会话名称查询、签到、定时消息、监听转发、群成员清理、AI 提供商请求与 TG 通知。启用后不受 `NO_PROXY` 绕过，连接失败也不会退回直连。

服务端的全局 `fetch` 与 Node.js HTTP/HTTPS 客户端自动使用代理；Node.js TCP 出口和全部 Python 执行器另有直连保护，未接入代理的连接会被拒绝，避免模块遗漏导致直接上网。该设置管理项目运行时的联网，不会修改电脑或浏览器的系统代理，也不控制 Docker 拉取镜像、构建时安装依赖的网络。

浏览器访问网页属于入站连接，Compose 内部 PostgreSQL 属于数据存储连接，保留正常通信；数据库负责读取代理配置并持久化任务。若自行配置外部 PostgreSQL，它的存储连接也保留直连，因此此设置不用于代理远程数据库。

保存代理或更改系统默认出口会停止并重新连接消息监听，同时取消尚未完成的名称查询。签到、扫码登录或群清理正在运行时暂不允许修改，需等待结束，避免任务途中切换出口。密码不回显，留空保存保留已有密码；取消认证时勾选「清除已保存的代理密码」，并清空用户名。

代理列表、默认出口和 AI 提供商保存在 PostgreSQL 的 `system-settings` 文档，文件模式使用数据目录 `.system-settings.json`；账号出口及用户的 AI 选择保存在各自配置。重启、重新部署及旧文件迁移都会保留。已有单代理自动迁为「原系统代理」，原默认启用状态保留；稳定 ID 保证改名或调整列表顺序不会改变账号选择。普通用户可管理自己的全局代理列表；管理员共享代理仅提供名称和协议，不能获取其地址或认证信息。用户设置默认代理后，仅重新连接该用户的监听任务，其他用户的连接保持运行。

Docker 内的 `127.0.0.1` 指向应用容器自身。连接宿主机上的代理使用 `host.docker.internal`（Compose 已配置宿主机映射），代理需允许容器网络连接；代理在另一个容器时可填写对应服务名。更新后执行 `docker compose up -d --build`，安装新增的 AI SOCKS5 传输依赖。

### 管理员后台审计

管理员打开「后台审计」，选择网页用户后查看其所有 Telegram 账号，也可按单个账号筛选。在「签到日志」查看手动签到、账号定时与 Bot 独立定时的日志，支持日期（北京时间）和运行状态筛选、重置及刷新；在「Bot 配置」查看签到方式、命令、备注、独立定时，以及对话分组已有的识别记录。使用分组时会提示手动 Bot 列表暂不执行。移除的 Telegram 账号若仍有签到日志，可通过历史账号选项查看。

审计读取已持久化的配置与签到日志，沿用现有日志保留数量；运行中的日志也可刷新查看，无需新增数据库表。审计仅支持查看，不提供执行或修改用户任务的入口。普通用户无法调用审计接口；管理员查看不会切换自己的工作空间，不返回 API Hash、AI Key、密码或 Session 文件，日志中的已知服务密钥与登录令牌会隐藏。已删除网页用户不在审计列表中。

### TG 任务结果通知

打开「TG 通知」，启用开关，填写从 @BotFather 获取的 **Bot Token** 和接收 **Chat ID**，保存后可点击「发送测试通知」。支持个人数字 ID、群组数字 ID（通常为负数）或公开频道 @用户名。私聊先向通知 Bot 发送 /start，群组或频道需允许该 Bot 发消息。通知通过 Telegram Bot API 发送，无需 Telegram 账号 Session；服务器需能访问 api.telegram.org。Token 保存后不回显，输入留空保留原值。

每次账号定时签到、Bot 独立定时结束时发送通知，包含账号、任务、结果、结束时间和耗时；成功、失败、停止均会通知，启动失败也会通知。手动签到、定时消息及持续监听转发暂不发送结果通知。通知使用纯文本汇总：先列未完成 Bot，再列成功及跳过项目，附北京时间和耗时。有备注显示 `✅ 备注（Bot 名称）`，无备注显示 `✅ Bot 名称`；超时显示 `⏰ 备注（Bot 名称）：超时`。

网页日志按任务和账号分组，每组只显示一次任务状态及统计。部分 Bot 成功、部分超时或失败时显示「部分成功」，不再将成功 Bot 标为运行失败；筛选和管理员审计也支持「部分成功」。新日志保存每个 Bot 的最终结果及执行时的备注，旧日志的汇总行仍兼容识别。格式集中在 `checkin_results.js` 与 `telegram_notifications.js`。

各网页用户的通知配置、发送队列和记录独立持久化：PostgreSQL 使用对应工作空间的 notifications 文档，文件模式使用 .notifications.json，切换数据库时自动迁移。通知先保存队列再发送；发送失败不会改变原任务结果。网络故障、Telegram 限流及服务端错误最多尝试 3 次，无效 Token 或权限错误直接记录失败；页面显示最近 20 条发送记录。每次运行以执行 ID 去重，已确认发送的任务重启后不会重复通知；请求超时或进程中断导致 Telegram 接收状态不明时，重试可能产生重复消息。关闭通知或更换接收配置会取消尚未发送的旧队列，已经发送中的请求可能仍完成。

升级后，原有配置、Telegram Session 和日志继续属于管理员，无需移动文件。新用户从空配置开始，即使不同用户采用相同 Telegram Session 名称，也使用各自的 Session 文件和数据库文档。每个用户的后台任务独立运行，不因网页退出登录而停止。

Compose 的 PostgreSQL 保存用户记录（随机盐与 scrypt 密码摘要）、用户配置、日志、调度状态、资料和识别记录。普通用户数据库文档使用 `tenant:<用户ID>:` 前缀，网页无法指定或切换该前缀；Telegram Session 仍是持久化文件，位于 `data/.user-workspaces/<用户ID>/`，管理员原目录保持兼容。备份须同时保存 PostgreSQL 与整个 `data/`。

未配置 PostgreSQL 时，文件模式将用户记录写入数据目录的 `.web-users.json`，普通用户全部数据写入 `.user-workspaces/<用户ID>/`。之后切换 PostgreSQL 时会在事务中导入用户记录及各用户的数据，源文件保留；已有数据库记录不会被旧文件覆盖。已使用 PostgreSQL 的项目直接升级即可。

## 快速开始：本机运行

## 首次配置与登录

1. 在「全局设置」配置自己的 Telegram API ID / API Hash，再到「账号管理」添加账号并填写名称、Session 名称。账号 API 字段留空会逐字段继承全局，也可填写独立覆盖；未配置个人全局 API 时继承管理员配置。API 凭据可从 [my.telegram.org](https://my.telegram.org) 获取。
2. 保存账号配置。登录不需要 Bot 或 AI 服务。
3. 点击账号卡片的「登录」或账号资料中的「登录 Telegram」，使用手机 Telegram 的「设置 → 设备 → 连接桌面设备」扫描网页二维码；启用两步验证时，在弹窗中输入密码。
4. 登录成功后等待登录进程退出并刷新 Session 状态，弹窗自动关闭；失败或两步验证密码错误保持可见。二维码过期会自动刷新；可取消登录，刷新网页也可恢复进行中的登录弹窗。登录独立进程不执行签到，密码不写入配置或日志。
5. 打开「功能中心 → Bot 自动签到」，选择账号并配置 Bot、添加定时计划或手动执行。账号与批量手动执行均留在插件页面，打开本次执行的实时小日志窗口；关闭窗口不会停止任务，窗口内停止按钮需二次确认。

### 运行日志

账号卡片的「日志」按钮和账号配置中的「运行日志」菜单均在原页面弹窗展示当前账号日志，关闭后保留原来的账号列表或配置页面。弹窗带平滑开关动画，可点击关闭按钮或按 Esc 关闭；账号固定为当前账号，重置筛选也不会切换到其他账号。顶部导航的「运行日志」仍使用完整页面，默认显示全部账号，可自行选择单个账号。

日志分类下拉框提供「定时任务」「定时消息」「监听转发」三类及「全部分类」。定时任务包含账号与 Bot 签到，也保留手动执行记录；另外两类记录规则执行结果和错误。可组合选择分类、账号、日期、开始/结束时间（精确到秒）和运行状态，点击「筛选」查看，也可「重置筛选」。时间统一按北京时间，时间边界包含该秒；筛选不会清除原日志。日志页不提供开始签到或停止任务按钮，本次签到弹窗仍可停止对应任务。

新批量签到日志带有每行所属账号和各账号的执行结果，可在单个账号下查看自己的部分；某账号失败不会把其他成功账号的日志标为失败。旧批量记录中没有账号标记的内容只在全局日志显示。定时消息和转发的旧临时日志无法补录，升级后开始持久化。

三类日志在 PostgreSQL 模式下保存在数据库的 `run-history` 文档，文件模式下保存在数据目录 `logs/run-history.json`，无需新增数据库表或手动迁移。日志更新最多每 250 毫秒合并保存，签到结束立即保存。签到保留最近 30 次执行、最多总计 3000 行、每次最多 800 行；定时消息与转发另保留最近 1000 条事件。每行最多 2000 字符。重启后未完成的签到标为失败/中断；消息和转发事件保留当时的结果。落盘失败会在服务日志报告。日志可能含 Telegram 消息内容，请限制数据库、数据目录及备份的访问。

Session 名称需与网页完全一致，只能包含字母、数字、下划线、点和连字符，不允许路径。**修改 Session 名称不会自动迁移原文件**。存在 Session 文件也不代表凭据仍有效，失效后需要重新登录。

### 并发签到

- 不同网页用户可以同时签到；各自的运行进程、Session 目录、数据库文档、日志与通知队列独立。不同用户使用相同 Session 名称也不会共用文件。
- 同一网页用户的不同 Telegram 账号可以同时签到，在签到插件切换到空闲账号后仍可执行；「全部账号签到」会并行处理全部账号，每个账号内部的 Bot 仍依次执行，间隔 5–15 秒。同秒触发的不同账号计划可以在同次调度检查中启动，忙碌账号不会阻塞其他账号。
- 同一个账号的整体签到、Bot 独立签到与手动签到共享 Session 锁。定时任务在该账号忙碌时排队，前一任务结束后等待 5–15 秒再启动；同账号重复手动启动会提示任务正在运行，不会自动排队。不同账号互不等待冷却时间。手动签到或登录抢先占用时，已排队的定时任务继续等待，不因竞争被丢弃。
- 每个运行任务使用独立 ID 与日志；任务弹窗中的「停止」只停止对应任务。批量签到会锁定全部所选账号，不能再重复单独启动；批量中一个账号失败时其他账号继续执行，成功账号的日志保留各自结果。
- 签到与登录使用同一工作空间互斥；签到与已有定时消息、监听转发、抢红包复用 Telegram 连接并行运行，同一 Session 文件只由一个进程打开。停止单次签到不停止监听，混合批量签到可同时使用监听连接与其他账号的独立签到进程。运行期间不能保存配置或同步 Telegram 资料。
- 以上保证适用于当前单应用实例部署。不要让多个应用实例或手动运行的脚本同时使用同一数据目录/数据库；运行锁不是分布式锁。不同网页用户若添加同一个实际 Telegram 账号，仍可能重复向同一 Bot 发送签到消息；共享 API 或 AI 服务也受服务商限流约束。

## Docker Compose + PostgreSQL

同一个 `docker-compose.yaml` 部署源码构建的应用与 PostgreSQL 17。数据库不发布宿主机端口，应用等待数据库健康后启动。

```bash
mkdir -p data
# Linux 上确保 UID 1000 可写。Windows 使用 Docker Desktop 无需 chown。
sudo chown 1000:1000 data
cp .env.example .env
# 编辑 .env，分别设置 ADMIN_PASSWORD 和 POSTGRES_PASSWORD；不要提交 .env。
docker compose up -d --build
docker compose logs -f autocheckin
```

打开 **http://服务器IP:8765**（本机也可用 `http://127.0.0.1:8765`）；Compose 默认发布 `8765:8765`，无需配置域名白名单。首次构建会安装 Node/Python 依赖。配置和记录保存在 PostgreSQL 命名卷 `postgres-data`；`./data:/data` 保留 Telegram Session 文件和首次迁移的旧文件。普通 `docker compose down` 会保留数据，`down -v` 会删除数据库卷，不应作为日常更新命令。

更新代码：

```bash
git pull --ff-only
docker compose up -d --build
```

### 从旧数据迁移

1. 停止原服务并备份原数据目录，确保没有其他实例占用 Session。
2. 将 `config.json`、`*.session`、`.automation-state.json`、`.checkin-schedule-state.json`、`logs/run-history.json`、`.account-profiles/` 以及已有 `.bot-discovery/` 放入 `data/`，保留原目录结构。旧版已有 `data/` 的可继续使用。
3. 设置 `.env` 的两个密码并运行 `docker compose up -d --build`。首次启动在数据库事务内导入所有现有文件，源文件不删除；异常 JSON 会中止迁移，不做部分导入。日志会显示导入数量。
4. 后续启动以数据库为准，不会用旧文件覆盖数据库。修改旧 `config.json` 不再影响数据库模式；请使用网页配置。旧 Bot 备注、账号计划和分组字段保持兼容，分组入口改在 Bot 管理。

数据库使用 `autocheckin_documents` 表和 JSONB 文档保存兼容配置结构。首次导入标记为 `migration:files-v1`；迁移失败修复源文件后重启即可。已有数据库配置不会被自动导入覆盖。

### 备份与恢复

备份前停止应用，数据库保持运行：

```bash
docker compose stop autocheckin
docker compose exec -T postgres pg_dump -U autocheckin -d autocheckin > autocheckin-backup.sql
# 同时备份整个 data/，包含 Telegram Session 文件。
docker compose start autocheckin
```

恢复数据库到空的新数据库时使用 `psql -U autocheckin -d autocheckin < autocheckin-backup.sql`，同时恢复 `data/` 后启动应用。SQL 备份含账号凭据和日志，应与 Session 一起妥善保存；不要上传 GitHub。

## Bot 定时与分组使用

### 配置单个 Bot 的独立定时

1. 打开「功能中心 → Bot 自动签到」，选择执行 TG 账号，进入「Bot 管理」。
2. 将「Bot 来源」设为「手动配置列表」，添加 Bot 用户名，选择按钮或命令签到方式；需要时填写命令和备注。
3. 在该 Bot 的「独立定时 · 北京时间」一栏开启「独立」开关，并设置每日执行时间（时、分、秒），例如 `21:30:15`。
4. 保存配置后生效。不同账号可以分别设置同一个 Bot 的签到方式、备注和时间。

独立定时采用横向布局：**开关 → 独立 → 时间框**，手机端也保持同一行。

| 开关状态 | 执行方式 |
| --- | --- |
| 灰色关闭 | 时间框禁用，Bot 参与账号整体签到，包括账号计划、账号手动签到和批量手动签到。 |
| 绿色开启 | 每天按此 Bot 的独立时间签到，不参与账号整体定时计划；账号手动签到和批量手动签到仍会执行此 Bot。 |

手动执行始终包含当前来源下的独立定时 Bot，可用于失败后补签；不改变其独立定时时间或自动任务的领取记录。日志会标明「手动签到」「账号整体定时」或「Bot 独立定时」。账号整体定时跳过独立 Bot 时会说明原因及其执行时间；如果显式指定的 Bot 不在当前账号可签到列表中，则记录为失败，避免未执行却报告成功。命令行默认手动执行；`--scheduled` 标记自动任务，`--account SESSION --bot @BOT --scheduled` 执行指定 Bot 的独立定时。

Bot 独立定时支持 `HH:mm:ss`（时、分、秒），旧配置 `HH:mm` 仍兼容，秒默认为 `00`。时间选择弹窗提供时、分、秒三列。调度器每秒检查，到达指定时间后入队；忙碌时按队列延后执行。

Bot 独立定时使用每日固定时间，全部按 **北京时间（UTC+8）** 执行；账号「定时任务管理」中的计划另外支持每日、一次性以及每日区间随机。独立定时也进入同一签到队列，忙碌时可能延后开始；服务停机错过触发窗口不会补跑。

### Telegram 对话分组轮询

在「功能中心 → Bot 自动签到」选择账号，在「Bot 管理」把「Bot 来源」改为「Telegram 对话分组」，填写分组名称或数字 ID 并保存。开启后只轮询分组内的 Bot，手动配置列表及其独立定时暂停。

- 首次运行依次探测按钮、`/sign` 和 `/checkin`，识别记录按账号保存，后续直接复用已确认的方式。
- 已确认没有签到方式的 Bot 后续跳过；无有效响应或网络失败保留为待确认。
- 在「分组识别记录」可查看方式和最近结果；「刷新记录」更新列表，「重新识别」清除对应 Bot 的记录，下次运行重新探测。
- 每个 Bot 处理完成后随机等待 **5–15 秒**，再处理下一个 Bot。

弹窗、确认框、下拉菜单和日期时间面板均支持平滑开合，并尊重系统的减少动态效果设置。

## 定时任务与转发规则

所有计划均按 **北京时间（UTC+8）** 计算，不随浏览器时区变化。

- **每日任务**：支持固定时间或每日区间随机；触发窗口见下方「秒精度与每日区间随机」，停机错过后不补跑。
- **一次性任务**：仅在指定时间之后 5 分钟内触发，过期不补跑。
- **签到排队**：与手动签到互斥，已触发任务在忙碌时排队；持久化触发记录用于避免重启后再次触发。触发记录不等于 Telegram 签到成功。
- **消息自动化**：使用规则所属账号的 Session；签到复用其连接，批量签到期间已有监听继续运行。登录、群清理或配置变更造成的暂停期间，监听消息不保证补转发。
- **转发会话**：支持公开用户名（可带 `@`）、公开 `https://t.me/用户名` 或数字会话 ID（频道常见 `-100…`），不支持私有邀请链接。账号必须有读取来源、发送至目标的权限。
- **规则校验**：拒绝同源同目标与可检测的同账号转发循环。不同账号之间、或同一会话使用不同标识时的循环仍需自行避免。

PostgreSQL 模式保存调度触发和发送记录；文件模式分别保存到 `.automation-state.json` 与 `.checkin-schedule-state.json`。**这不是严格的 exactly-once 保证**：在 Telegram 操作与本地写盘之间发生崩溃时，仍可能遗漏或重复执行。

服务停止后所有自动任务及进行中的登录停止；任务必须已有可用 Session，可先在网页完成 Telegram 登录。

### 秒精度与每日区间随机

定时签到和定时消息均支持固定 `HH:mm:ss`，旧的 `HH:mm` 仍可读取；一次性任务支持 `YYYY-MM-DDTHH:mm:ss`（仅固定时间）。每日任务可选择区间随机：

```json
{"id":"random_example_01","enabled":true,"repeat":"daily","timeMode":"random","rangeStart":"09:00:00","rangeEnd":"10:30:00"}
```

签到任务置于账号 `checkin_schedules`；消息任务还需 `account`、`target`、`message`，置于 `automations.schedules`。固定任务使用 `timeMode: "fixed"` 和 `time: "09:30:15"`。区间接受 `HH:mm` 或 `HH:mm:ss`，包含两端，开始等于结束合法；**不支持跨午夜**，开始晚于结束会明确拒绝。

- 全部按北京时间（UTC+08:00）计算，每个账号/规则每天独立抽取整数秒。抽中时间在 UI 显示为 **HH:mm:ss**，只刷新结果，不覆盖正在输入的表单。
- 当天抽取结果在 PostgreSQL 模式下写入数据库，文件模式保存到 `.checkin-schedule-state.json` / `.automation-state.json`，重启不重抽；第二天重新抽取。修改尚未触发的区间会重新抽取；已触发/领取的当天任务不会因修改区间重复执行。禁用或删除会清理抽取计划。
- 计划和执行领取记录必须成功原子写入后才允许执行。消息采用领取后至多一次尝试策略：发送失败、领取后进程退出或取消均不自动重发，避免未知发送结果造成重复；可手动新建一次性任务处理。
- 服务每约 1 秒检查。旧每日 `HH:mm` 保留当分钟 60 秒窗口；每日固定秒和随机任务只在抽中时刻起 **10 秒内**领取（区间结束限制的是抽取时间，不是执行截止，终点抽取仍有 10 秒领取窗口）；一次性任务维持 5 分钟窗口。超过窗口的停机/暂停任务**不补跑**。新启动抽取到过去且超窗的时间也不补跑。
- 签到在窗口内领取后可排队等待忙碌任务完成，实际开始可能晚于抽取时间。Telegram 连接、网络、限流和事件循环负载也会造成延迟，秒精度是计划精度，不承诺实时准点。
- 随机消息需要自动化 worker 成功启动；未登录/环境不可用时不会生成新抽取结果，UI 显示等待。暂停期间可显示已持久化的当天结果。

### 监听转发：自动显示会话名称

1. 打开「功能中心 → 监听转发并置顶 → 配置插件」，添加规则并选择执行 TG 账号。
2. 在「来源群组 / 频道」和「转发到」填写会话 ID、公开用户名或公开 `https://t.me/用户名` 链接。停止输入后自动查询，无需先保存规则。
3. 查询成功时，输入框右侧显示群组或频道名称；长名称会省略，鼠标悬停可查看完整名称、类型及 ID。打开已有规则时也会自动查询。
4. 按需设置关键词和置顶开关，启用规则并保存后，使用所选账号监听来源的新消息并转发到目标。

名称查询使用当前账号已登录的 Telegram Session，结果按账号分别缓存；名称仅作确认提示，不会替换输入的会话标识，也不会自动加入群组或频道。查询失败时右侧显示原因，请检查登录状态、网络、会话标识及账号访问权限。显示名称不代表账号有目标发送权限。

## 环境变量

`ADMIN_USERNAME`：管理员用户名，默认 `admin`；不能与已创建的普通用户重名。`ADMIN_PASSWORD` 仍为管理员密码。

- `PGHOST` / `PGPORT` / `PGDATABASE` / `PGUSER` / `PGPASSWORD`：PostgreSQL 连接参数。设置 `PGHOST` 后启用数据库模式，也支持 `DATABASE_URL`。Compose 已自动配置，密码来自 `.env` 的 `POSTGRES_PASSWORD`。
- `PORT`：监听端口，默认 `8765`。
- `ADMIN_PASSWORD`：必填，只从环境读取，不通过配置 API 返回或保存。修改后重启服务，现有会话失效。
- `TRUST_PROXY`：默认 `false`；明确设为 `true` 后信任单一 `X-Forwarded-Proto: https`，支持独立服务器反代和 Docker bridge 来源。仅在上游反代会覆盖此头且已控制后端直接访问时开启；不信任 `X-Forwarded-Host`、`Forwarded` 或转发 IP，代理下登录限流按代理统一计算。Compose 可在 `.env` 设置此变量。
- `AUTOCHECKIN_DATA_DIR`：配置、Session 和状态所在目录；本机默认项目目录，Compose 为 `/data`。
- `PYTHON_BIN`：Python 解释器路径，例如 `/usr/bin/python3`。
- `BIND_HOST`：监听地址，默认 `0.0.0.0`，允许通过所有 IPv4 网卡访问；仅需本机访问可设为 `127.0.0.1`。
- `STRICT_PUBLIC_HOST`：默认 `false`，不启用固定域名/端口白名单；设为 `true` 才恢复旧版 Host 精确限制，不影响密码认证或同源检查。
- `PUBLIC_HOST` / `PUBLIC_PORT`：仅用于 `STRICT_PUBLIC_HOST=true` 时的请求 Host 限制，格式为 `${PUBLIC_HOST}:${PUBLIC_PORT}`（始终包含端口）；默认分别为 `127.0.0.1` 和 `PORT`。`PUBLIC_HOST` 不是完整 URL，也不是客户端 IP 白名单。

Linux 指定端口示例：

```bash
PORT=9000 PYTHON_BIN=/usr/bin/python3 ADMIN_PASSWORD="replace-with-a-long-random-password" node server.js
```

此时访问 `http://127.0.0.1:9000`。远程管理建议通过 SSH 隧道：

```bash
ssh -N -L 8765:127.0.0.1:8765 user@服务器
```

HTTPS 反代必须保留浏览器的 `Origin` 和原始 `Host`（含非默认端口），覆盖设置 `X-Forwarded-Proto: https`，并在 AutoCheckin 设置 `TRUST_PROXY=true`。例如浏览器访问 `https://ack.wyattu.net`，转发给后端的 Host 应为 `ack.wyattu.net`，而不是后端 IP 或 `:8765`；无需设置 `PUBLIC_HOST`。反代可在独立服务器上，不需要在 AutoCheckin 主机安装 Nginx。服务按真实 Host 与协议校验修改请求的 Origin，忽略 `X-Forwarded-Host` / `Forwarded`，因此这些头不能绕过跨站校验。

直接 HTTP 访问不需要 `TRUST_PROXY`。公开环境应使用 HTTPS 反代；开启代理信任时，请用防火墙/安全组限制后端直连来源为可信代理，并确保代理覆盖协议头，不透传客户端伪造值。这是部署建议，不是应用内置 IP 限制。若仅需本机发布，可自行把 Compose 端口改为 `127.0.0.1:8765:8765`。

登录接口为 `/api/auth/login`，与 Telegram 的 `/api/login/*` 独立。会话采用随机令牌、HttpOnly / SameSite=Strict Cookie，可信 HTTPS 下附加 Secure；12 小时固定到期，不滑动延期，重启或退出登录立即失效。最多 256 个会话；登录错误每个可信连接 IP 15 分钟最多 10 次，最多跟踪 2048 个 IP。密码不写入浏览器存储，无“记住密码”。所有管理 API（包括 Telegram 登录状态/密码接口）和后台 HTML/JS 均需会话，只有登录页面、其资源和共享样式公开。

## 数据、安全与备份

- 账号密钥、AI Key 保存于 PostgreSQL（文件模式保存于数据目录），Session 相当于账号登录凭据。限制数据库和目录访问权限，保护 SQL 备份和 Session 文件。
- 全局 API Hash、账号已有 API Hash / AI Key 不回显，输入框留空保存保留已有密钥。账号资料中的「使用全局凭据」会在保存时清空该账号 ID / Hash 覆盖；只清空 Hash 可用「清空账号 Hash 覆盖」按钮。取消开关可继续设置独立覆盖。
- 配置文件全局字段为 `telegram.api_id` / `telegram.api_hash`；账号 `api_id` / `api_hash` 缺失、空字符串或 null 时逐字段继承全局。已有账号默认保持独立覆盖，不会自动选择其凭据作为全局值。所有 Python 执行路径在运行时解析凭据，不把全局 Hash 复制进账号配置。
- 运行中的签到使用启动时读取的配置；启动及运行期间拒绝配置保存和自动化重启，避免争用 Session。
- 签到、定时消息和转发日志均持久化，保留范围见「运行日志」；自动化界面的实时状态仍有独立的有限内存缓冲。
- 旧版顶层 `bots` / `bot_groups` / `bot_notes` 会作为账号初始配置读取，首次网页保存后迁移到账号独立配置。
- 备份前停止服务，再备份整个数据目录；恢复时保持 Session 名称、文件名和目录权限一致。
- `.gitignore` 排除真实配置、Session、虚拟环境与缓存，但不能撤销 Git 历史中的泄露；若曾提交真实凭据，应立即轮换密钥并撤销泄露的登录会话。

## 常见问题

**页面返回 403**：默认不限制域名/访问 IP；检查是否意外开启 `STRICT_PUBLIC_HOST`。HTTPS 反代需保留原始 Host / Origin，设置 `X-Forwarded-Proto: https` 并开启 `TRUST_PROXY=true`；不同源的修改请求仍会被拒绝。

**未找到 Python / 缺少依赖**：用服务实际选择的解释器安装 `requirements.txt`，必要时设置 `PYTHON_BIN`，重启服务。解释器探测有短时间缓存。

**Docker 提示 Permission denied**：检查 `data/` 是否允许 UID 1000 写入；不要用 `chmod 777` 代替权限管理。

**无法运行签到**：确认账号有 Bot、已完成登录、Session 文件位于数据目录；查看日志中的实际错误。

**某个 Bot 失败**：先确认命令和交互模式；验证码或界面变动可能需要适配。`MAX_FAILED_ROUNDS` 当前为 `0`，首轮失败后不进入额外重试轮次，但会继续后续账号。

**定时任务没有补跑**：检查北京时间、启用状态、服务运行状态和上述触发窗口；不要直接删除状态文件来“修复”，这可能导致重复执行。

## 开发与离线测试

```bash
python3 -m pip install -r requirements.txt
node tests/run-tests.js
```

测试使用隔离配置、模拟客户端与本地服务，不需要真实 Telegram / AI 凭据，不会执行真实签到或发送消息。本仓库已关闭 GitHub Actions，测试可通过本地命令执行。

离线回归覆盖数据库缓存读写顺序、写入失败恢复、名称查询进程超时和停止清理，以及 OCR 按需加载。`tests/polling-browser-test.js` 使用模拟接口检查状态刷新、隐藏页面停止查询、草稿保留和账号切换；需要 `PLAYWRIGHT_MODULE`，可通过 `PLAYWRIGHT_CHROMIUM_EXECUTABLE` 指定本机 Chromium 路径。

PostgreSQL 集成测试通过 `AUTOCHECKIN_TEST_DATABASE_URL` 显式指定测试服务器，会创建并删除独立测试数据库；不要指向生产服务器。测试覆盖原子迁移、失败回滚、重启不覆盖旧数据、Node/Python 共享存储及网页配置保存。

测试入口优先使用项目 `.venv`，也可通过 `PYTHON_BIN` 指定解释器；Windows 控制台统一使用 UTF-8。可选 Chromium 页面测试需要设置 `PLAYWRIGHT_MODULE` 为已安装 Playwright 模块的路径，未设置时会明确跳过。页面控件支持键盘操作：下拉菜单使用方向键、Enter 和 Escape；日期时间输入可直接键入，也可点击右侧图标使用主题日历与秒级时间选择器。

## 账号头像与资料

账号卡片会显示 Telegram 头像、用户 ID 和当前 Session 的数据中心（DC）。登录成功后自动同步；已有 Session 的账号在打开账号管理时补充获取一次，也可点击「同步资料」更新。无头像时显示名称首字；网络失败保留上次资料。同步与签到/登录互斥，自动化会在同步结束后恢复。资料保存在 PostgreSQL，文件模式使用数据目录的 `.account-profiles/`；这些缓存目录已从 Git 和 Docker 构建上下文排除。头像接口需要后台登录，缓存不保存手机号、API Hash 或 Session 密钥。
